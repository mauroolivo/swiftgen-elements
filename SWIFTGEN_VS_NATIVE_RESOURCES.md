# SwiftGen vs Native Resources

## Decision matrix (lab-grounded)

| Resource area | Native Xcode/Swift APIs | SwiftGen | Recommendation |
|---|---|---|---|
| App assets/colors (`.xcassets`) | Strong typed symbols in modern Xcode; automatic regeneration on build | Typed API and customizable shape; requires explicit regeneration workflow | Prefer native first for simple apps; use SwiftGen when API standardization/customization is needed |
| Localization (`.strings` / `.stringsdict`) | Works natively, but string-key usage can remain stringly at call sites | Typed keys and typed format arguments; catches call-site mistakes at compile time | Strong case for SwiftGen when staying on legacy strings formats |
| String Catalog (`.xcstrings`) | First-class native workflow in Xcode | Installed lab SwiftGen version had no direct `.xcstrings` parser command | Prefer native String Catalog workflow unless/ until direct support is required and verified |
| Swift package resources | `Bundle.module` is straightforward and explicit | Works for generated strings; package asset generation may require extra adaptation under strict concurrency checks | Use native `Bundle.module` baseline; add SwiftGen selectively per module |
| Build integration | No extra generator dependency | Requires tool availability + script inputs/outputs discipline | Use script integration only with explicit dependency declarations and CI checks |
| Team consistency | Simple defaults, less custom tooling | Consistent API style across modules, customizable naming/access | Use SwiftGen when cross-module consistency is a key goal |

## What we measured in this lab
- Native asset symbols were generated by Xcode and updated on build.
- SwiftGen config-driven generation was deterministic and lintable.
- Typed localization accessors caught argument-type misuse at compile time.
- Missing locale translations remained runtime/data concerns.
- Script sandboxing required concrete input files, not only broad directories.
- Wrong bundle boundaries in package code were detected by tests.

## Practical rules
1. Start with native APIs.
2. Add SwiftGen where typed accessors materially reduce defects (especially localization).
3. Keep one canonical config per module scope.
4. Enforce generation consistency in CI.
5. Test bundle boundaries in Swift package modules.

## Final recommendation
- **Use native only** when resource surface is small and team conventions are stable.
- **Use SwiftGen only** when typed API consistency is the primary objective and the team accepts generator ownership.
- **Combine both** (recommended baseline from this lab):
  - native for package/app asset and color access where already ergonomic,
  - SwiftGen for localization accessors where compile-time key/argument safety adds clear value.
